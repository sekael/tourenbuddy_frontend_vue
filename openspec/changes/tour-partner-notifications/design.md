## Context

The notification surface is mature: a client-side fire-and-forget dispatcher (`notify-dispatch.ts`) posts to the `email-hook` Worker, which resolves recipients and fans out push + email honoring per-user preferences. For shared tours, `tours-store` already calls `notifyTourChanged(id, 'created' | 'updated')` and `notifyTourDeleted(...)`, and the Worker `handleTourChanged` resolves `partners ∩ owner-friends − actor`.

The one behavioral wrinkle (Issue #210): adding a partner to an **existing** tour flows through `updateTour` → `notifyTourChanged(id, 'updated')`, so a brand-new partner's first notification is *"X updated tour Y"* instead of *"X shared Y with you"*. The create path is fine; only the edit-add path mis-greets.

There is also no consolidated documentation of what notifications exist — the second half of the story.

## Goals / Non-Goals

**Goals:**
- A partner added during an edit receives the `created` ("shared with you") copy; pre-existing partners still get `updated`.
- A single `docs/notifications.md` documenting every notification (trigger, actor, recipients, type, copy EN/DE, mute key, call site).
- Reuse existing primitives (`resolveUsersByContactIds`, `dispatchTourNotification`) — no new notification type, no schema change.

**Non-Goals:**
- Notifying a **removed** partner ("you were removed from tour X"). Documented as a known gap, not implemented.
- Changing email templates or copy strings (the `created` template already exists).
- Any DB/migration/env change.

## Decisions

### 1. Reuse `created` copy rather than a new `partner_added` action
The chosen approach (per #210 review): when an edit adds partners, the newly-added friend partners get the existing `created` notification; everyone else gets `updated`. This avoids a new action type, new copy strings, and new email template — the `created` path is already wired end-to-end. Trade-off vs. a dedicated `partner_added` action: the new partner sees "shared with you" (semantically a fresh share, which is accurate) rather than an explicit "added you as partner". Acceptable and cheaper.

### 2. Client computes the added-partner set; Worker splits recipients
`updateTour` already holds both `existing.partnerIds` and `draft.partnerIds`. It computes `addedPartnerIds = draft.partnerIds \ existing.partnerIds` and passes them to `notifyTourChanged` as an optional `newPartnerContactIds` argument. The Worker remains the authority on recipient resolution (never trust client for the full set): in the `updated` branch it resolves `newPartnerContactIds` to user ids via the existing `resolveUsersByContactIds`, intersects with the already-resolved `partners ∩ friends − actor` recipient set, and dispatches `created` to that subset and `updated` to the remainder. If `newPartnerContactIds` is empty/absent, behavior is identical to today (all recipients get `updated`).

Why split server-side rather than two client calls: a single round trip, the Worker already fetches the full recipient set once, and authorization/blast-radius stays bounded by the caller's own friendships (same guarantee as the delete path).

### 3. Documentation is a flat table in `docs/notifications.md`
One file, one table keyed by notification. Columns: trigger / actor / recipients / `notif` type / push title+body (EN/DE) / email template / mute key / client call site / Worker handler. Generated by auditing `notify-dispatch.ts` and the Worker `notify.ts`. A "Known gaps" section records the removed-partner non-notification.

## Risks / Trade-offs

- **Partner ids are contact ids, not user ids.** `draft.partnerIds`/`existing.partnerIds` are partner *contact* ids; the Worker resolves them to user ids. The set-difference is computed on contact ids (stable per tour), then resolved — consistent with how `notifyTourDeleted` already passes `partnerContactIds`. Verify the diff is on the same id space the Worker's `resolveUsersByContactIds` expects.
- **Double-greet edge:** if an edit both adds a partner AND changes a meaningful field, the new partner should get exactly one `created` (not `created` + `updated`). The server-side split (subset vs. remainder, mutually exclusive) guarantees this.
- **Docs drift:** a hand-maintained table can rot. Mitigated by keeping it terse and citing call sites so the next change author can find and update it; out of scope to auto-generate.
- **Worker deploy is manual and not in CI** — forgetting `wrangler deploy` ships the client change against a stale Worker that ignores `newPartnerContactIds` (degrades gracefully to all-`updated`, no error). Task list makes the deploy explicit.
